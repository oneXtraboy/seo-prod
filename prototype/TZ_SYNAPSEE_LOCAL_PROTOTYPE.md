# Техническое задание: автономный локальный прототип Synapsee

Версия: 1.0 — на проверку перед началом реализации  
Дата: 10 августа 2026 года  
Статус: реализация не начата

## 1. Предмет работы

Создать с нуля отдельный автономный интерактивный прототип обновлённого сайта Synapsee. Прототип должен визуально показывать будущую версию сайта после внедрения рекомендаций двух аудитов и использоваться как визуальное техническое задание для последующей ручной реализации.

Прототип не связан с production-сайтом и не изменяет `synapsee.ru`.

## 2. Цель

Собрать локальный сайт, который:

- быстрее объясняет, кто оказывает услугу, что получает клиент и чем отличается Synapsee;
- использует единое позиционирование независимой SEO-практики;
- показывает проверяемые доказательства вместо неподтверждённых обещаний;
- сокращает путь от первого экрана до обращения;
- остаётся узнаваемым относительно текущего Synapsee;
- одинаково понятно работает на desktop и mobile;
- открывает все 38 согласованных URL;
- служит наглядной основой для будущего production-внедрения.

## 3. Исходные материалы и их приоритет

Используются:

1. `SEO_UX_audit_synapsee_2026-08-07.docx`.
2. `UX_redesign_synapsee_2026-08-07.docx`.
3. Публичная версия `https://synapsee.ru/` на дату начала реализации.
4. Исходное текстовое поручение Фёдора.

Правила разрешения противоречий:

- аудиты определяют UX-проблемы, приоритеты и целевую структуру;
- публичный сайт служит источником наиболее свежего проверяемого контента, цен и доступных материалов;
- если текущий сайт уже содержит исправление из аудита, исправление сохраняется и не откатывается;
- если фактические сведения расходятся, используется более свежий проверяемый источник;
- любое существенное расхождение фиксируется в итоговом отчёте.

## 4. Границы проекта

### 4.1. Входит в работу

- новый локальный frontend-проект;
- 38 публичных маршрутов;
- переиспользуемая дизайн-система;
- девять основных типов страниц;

## 5. Формат запуска

Основной пользовательский сценарий:

1. Пользователь дважды нажимает `ОТКРЫТЬ_ПРОТОТИП.cmd`.
2. Запускается небольшой локальный сервер.
3. Браузер автоматически открывает локальный адрес прототипа.
4. Все маршруты, обновление страниц, переходы назад/вперёд и интерактивы работают как у обычного сайта.
5. После закрытия окна запуска локальный сервер прекращает работу.

Дополнительно предоставляются:

- команда разработки `npm run dev`;
- команда production-сборки `npm run build`;
- команда локального просмотра готовой сборки;
- `README.md` с короткой инструкцией.

Прототип не требует интернет-соединения во время обычного локального просмотра. Прямое открытие через `file://.../index.html` не является основным режимом.

## 6. Технологический подход

Базовый стек:

- Vite;
- React;
- TypeScript;
- клиентская маршрутизация;
- структурированные локальные данные страниц;
- локальные CSS-стили и ассеты;
- Vitest или эквивалент для ключевых компонентных сценариев.

Архитектурные требования:

- содержимое страниц отделено от шаблонов;
- одинаковые блоки не копируются между 38 страницами вручную;
- маршруты формируются из единого реестра;
- все runtime-данные находятся внутри проекта;
- отсутствуют скрытые сетевые запросы;
- отсутствие отдельных материалов не ломает страницу, а приводит к показу подписанного placeholder;
- проверка структуры маршрутов и внутренних ссылок выполняется без запуска браузера;
- сборка должна запускаться одной командой и не содержать ошибок.

## 8. Позиционирование и редакционные правила

Единая рабочая формулировка:

> Synapsee — независимая SEO-практика Фёдора Магери. Стратегия и контроль находятся у одного ответственного специалиста; разработчики, редакторы и профильные подрядчики подключаются по согласованной модели.

Требования:

- не называть Synapsee агентством, если речь идёт о субъекте ответственности;
- не использовать без пояснения смешение «я», «мы», «наша команда» и «частный специалист»;
- писать спокойно, конкретно и без агрессивной драматизации;
- не обещать фиксированные позиции и гарантированный результат;
- не выдавать корреляцию за причинность;
- не использовать цифры без периода, источника и контекста;
- каждое сильное утверждение сопровождается доказательством либо пометкой о необходимости подтверждения;
- существующий контент можно сокращать, переставлять и редактировать, сохраняя его фактический смысл.

## 9. Правила достоверности

Каждый факт относится к одному из статусов:

1. **Показатель с источником** — рядом указывается конкретная система данных.
2. **Цифра без источника** — не публикуется; карточка описывает выполненную работу качественно.
3. **Неподготовленный материал** — соответствующий блок скрывается до появления реального контента.

Запрещено создавать фиктивные:

- отзывы;
- логотипы клиентов;
- CRM-данные;
- скриншоты Метрики;
- сертификаты;
- договоры;
- графики результатов;
- фотографии Фёдора;
- рабочие документы, которые можно принять за реальные.

Не подтверждённые показатели кейсов можно показать только вместе с заметной подписью «Требуется подтверждение источником и периодом».

## 10. Визуальное направление

Рабочее определение: «спокойная современная экспертная практика».

Базовые ориентиры:

- основной фон: `#FFFFFF`;
- альтернативный фон секций: `#F6F8FB`;
- основной текст: `#172033`;
- основной акцент и CTA: `#2563EB`;
- зелёный применяется только к подтверждённым положительным результатам;
- красный применяется только к ошибкам и предупреждениям;
- радиус карточек: 16–20 px;
- тонкий нейтральный бордер;
- минимальные тени;
- один основной акцентный цвет;
- крупная, но не чрезмерная типографика;
- достаточно свободного пространства;
- реальные рабочие материалы либо честные placeholders.

Не использовать:

- чрезмерные градиенты;
- бессмысленные 3D-объекты;
- бегущие строки;
- фальшивые счётчики;
- автокарусели;
- параллакс;
- длинные декоративные анимации;
- стоковые рукопожатия;
- десятки одинаковых карточек;
- декор, мешающий чтению.

## 14. Формы

### Первый шаг

- поле «Адрес сайта»;
- одно поле «Telegram, телефон или email»;
- кнопка «Получить 3 точки роста».

Под формой:

> Без продажи на первом звонке. Ответ в течение рабочего дня. Данные не передаются третьим лицам.

Если срок ответа не подтверждён Фёдором, соответствующая часть помечается как требующая подтверждения.

### Второй шаг

- имя;
- задача;
- регион;
- комментарий;
- кнопка завершения.

### Поведение

- данные никуда не отправляются;
- сетевые запросы отсутствуют;
- обязательные поля имеют постоянные label;
- ошибки показываются рядом с полем и доступны screen reader;
- введённые данные сохраняются после ошибки;
- после завершения показывается локальный экран успеха;
- экран успеха прямо сообщает, что это демонстрация прототипа;
- закрытие модального сценария работает по Escape и возвращает фокус инициатору.

## 24. A/B-варианты без остановки основной сборки

Требование исходного поручения сохраняется, но не требует участия Романа как проектного менеджера.

Порядок:

- основной прототип сразу создаётся с рекомендуемым вариантом A: компактная форма находится в первом экране главной, типовой услуги и Pricing;
- это рабочий вариант прототипа, а не зафиксированный production-выбор Фёдора;
- на `/_prototype/variants/` размещаются варианты A и B для главной, типовой услуги и Pricing;
- вариант B использует CTA, который открывает форму или прокручивает к ней;
- для шести вариантов готовятся desktop- и mobile-состояния;
- реализация остальных 38 маршрутов не останавливается для согласования;
- исполнитель не открывает варианты в браузере и не объявляет их визуально проверенными;
- Роман проверяет варианты локально по отдельному чек-листу;
- после просмотра Фёдор может выбрать другой вариант, не затрагивая остальные шаблоны и контент.

Реальный A/B-тест, аналитика и статистический вывод в прототип не входят.

## 27. Разделение проверок качества

### Ответственность исполнителя

Исполнитель выполняет только проверки, не требующие открытия и управления браузером:

- анализ структуры проекта;
- проверку реестра маршрутов;
- проверку внутренних ссылок по данным и исходному коду;
- build, lint и unit/component tests;
- проверку отсутствия явно настроенных внешних отправок;
- проверку типов и статических ошибок;
- подготовку точного визуального чек-листа.

Исполнитель не запускает браузер, не открывает локальный preview, не кликает элементы, не меняет размеры окна, не инспектирует DOM визуально и не делает вывод о внешнем виде без подтверждения Романа.

### Невизуальные функциональные проверки исполнителя

- все 38 маршрутов присутствуют в реестре и собираются;
- служебный маршрут вариантов присутствует отдельно;
- внутренние ссылки не ссылаются на отсутствующие маршруты;
- компоненты меню, breadcrumbs, якорей, FAQ, фильтров и форм покрыты кодовыми проверками там, где это возможно без браузера;
- в формах отсутствует настроенная внешняя отправка;
- сборка вложенных маршрутов не содержит ошибок.

### Визуальные и интерактивные проверки Романа

- проверены заданные desktop/mobile-размеры;
- отсутствует горизонтальный overflow;
- нет перекрытий и обрезанного текста;
- sticky-элементы не закрывают важный контент;
- длинные H1 укладываются в заданные пределы;
- состояние фокуса видно;
- увеличение до 200% не уничтожает функциональность;
- меню, FAQ, формы, фильтры, якоря, Escape и кнопки назад/вперёд работают визуально и фактически;
- обновление каждого типа вложенного маршрута не приводит к ошибке;
- варианты A/B выглядят корректно на desktop и mobile.

Исполнитель передаёт Роману конкретный список маршрутов, размеров и действий. Роман запускает `ОТКРЫТЬ_ПРОТОТИП.cmd`, выполняет проверку и сообщает результаты. При необходимости Роман прикладывает скриншоты обнаруженных дефектов.

### Технические проверки исполнителя

- `npm run build` завершается успешно;
- lint завершается без ошибок;
- тесты ключевых компонентов проходят;
- отсутствуют явно настроенные внешние runtime-запросы;
- автоматическая статическая проверка внутренних ссылок проходит.

Проверка консоли браузера выполняется Романом по запросу исполнителя, если без неё нельзя диагностировать визуальную или интерактивную проблему.

## 28. Скриншоты и визуальная фиксация

Исполнитель самостоятельно не запускает браузер и не создаёт скриншоты.

Исполнитель подготавливает `VISUAL_QA_CHECKLIST.md`, в котором указывает:

- какие маршруты открыть;
- какой размер окна использовать;
- какие элементы нажать;
- что проверить визуально;
- какие скриншоты нужны по исходному поручению;
- рекомендуемые имена файлов и каталог сохранения.

Визуальную проверку и создание скриншотов выполняет Роман. Если полный комплект скриншотов остаётся обязательным для передачи Фёдору, он формируется Романом либо позже отдельным явно разрешённым действием.

Рекомендуемый комплект визуальной фиксации:

- полноразмерный desktop-скриншот каждого из 38 маршрутов;
- mobile-скриншот каждого основного шаблона при 390×844;
- отдельные desktop/mobile-скриншоты вариантов A и B для главной, услуги и Pricing.

Для проверки первого экрана дополнительно используется 1366×768.

## 31. Порядок выполнения

Кодовая часть выполняется одним автономным проходом. Визуальная приёмка всегда выполняется Романом:

1. Зафиксировать текущий публичный контент и материалы.
2. Создать проект и единый реестр маршрутов.
3. Собрать дизайн-токены и глобальные компоненты.
4. Создать основные шаблоны.
5. Применить рекомендуемый вариант первого экрана.
6. Добавить отдельную страницу A/B-сравнения для Фёдора.
7. Наполнить все 38 маршрутов.
8. Добавить интерактивные состояния.
9. Выполнить build, lint, unit/component tests и статическую проверку ссылок.
10. Подготовить локальный запуск и `VISUAL_QA_CHECKLIST.md`.
11. Попросить Романа запустить прототип и выполнить указанные визуальные и интерактивные проверки.
12. Получить от Романа список замечаний и, при наличии, скриншоты дефектов.
13. Исправить замечания без самостоятельного открытия браузера.
14. Повторно выполнить невизуальные проверки.
15. При необходимости попросить Романа повторить конкретные визуальные проверки.
16. Сформировать итоговые отчёты и передачу.

Исполнитель обязан остановиться и обратиться к Роману, если дальнейшее решение зависит от визуального результата, поведения компонента в браузере или подтверждения исправления. Самостоятельно открывать браузер вместо такого запроса запрещено.

## 32. Критерии приёмки

Прототип принимается, если:

- запускается через `ОТКРЫТЬ_ПРОТОТИП.cmd`;
- открывает все 38 маршрутов;
- работает без деплоя и изменения настоящего сайта;
- не отправляет данные наружу;
- показывает уникальное релевантное содержание каждого маршрута;
- использует единое позиционирование;
- не содержит выдуманных доказательств;
- явно маркирует неподтверждённые данные и placeholders;
- содержит все обязательные шаблоны и компоненты;
- работает на desktop и четырёх заданных mobile-размерах;
- по результатам проверки Романа не имеет горизонтального overflow;
- по результатам проверки Романа основные функции доступны с клавиатуры;
- содержит A/B-страницу для последующего выбора Фёдором;
- проходит build, lint, невизуальные тесты и статическую проверку ссылок;
- содержит итоговые отчёты и визуальный чек-лист;
- визуальная часть считается принятой только после явного подтверждения Романа;
- комплект скриншотов считается отдельным пользовательским результатом и не создаётся исполнителем без нового явного разрешения.

## 33. Зафиксированные решения

- Деплоя не будет.
- Production-сайт не изменяется.
- Основной запуск — локальный сервер через CMD-файл.
- Основной стек — Vite + React + TypeScript.
- Обязательный объём — 38 маршрутов.
- Основная визуальная версия создаётся по профессиональному усмотрению исполнителя и рекомендациям аудитов.
- Вариант A с формой в первом экране используется как рабочий рекомендуемый вариант.
- A/B-сравнение сохраняется для Фёдора, но не останавливает работу.
- Реальное A/B-тестирование не проводится.
- Недостающие факты и материалы заменяются только честными placeholders.
- Роман не участвует в промежуточном управлении дизайном, но является единственным исполнителем визуальной и интерактивной проверки.
- Исполнитель не запускает браузер, не управляет им, не кликает прототип и не выполняет визуальную QA-проверку.
- При необходимости визуальной проверки исполнитель просит Романа открыть конкретный маршрут, выполнить конкретные действия и сообщить результат.
